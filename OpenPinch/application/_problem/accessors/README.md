# Problem accessors

## Overview
Private accessor namespaces that `PinchProblem` exposes as `target`, `design`, `plot` and `components`. Each is a non-data descriptor that builds a new accessor bound to the problem instance on every attribute access. The accessors hold no state of their own beyond the problem reference; they delegate to the targeting services, the HEN synthesis services, the presentation graph accessor and the process component factory. `OpenPinch/application/problem.py` imports the four descriptors; `OpenPinch/application/commands.py` imports `HeatExchangerNetworkDesignView` and `UtilityChoiceError`.

## Interface
- `_TargetAccessorDescriptor` (`target.py`): binds `_TargetAccessor`, the descriptive targeting workflows (direct, indirect and total-site integration, `all_heat_integration`, Carnot / vapour-compression / MVR heat pumps and refrigeration (`brayton_heat_pump` and `brayton_refrigeration` exist but raise `NotImplementedError`), Carnot and simulated ORC, area and cost, cogeneration variants, exergy, energy transfer, utility placement, `heat_recovery_dt_min`, `hpr_load_kinks`, `hpr_performance_map`, `hpr_refrigerant_screen`), and `heat_pump_and_refrigeration`, the gateway every heat pump and refrigeration method runs through, with `hpr_cycles` describing the registered cycles.
- `_AllPeriodsTargetAccessor` (`target.py`): returned by `target.all_periods`; mirrors catalogued target methods once per canonical period, with a `workers` keyword; `utility_placement`, `heat_recovery_dt_min` and `hpr_load_kinks` are explicit methods. Its forwarders are generated by `install_catalog_forwarders`.
- `_DesignAccessorDescriptor` (`design.py`): binds `_DesignAccessor`: `heat_exchanger_network`, `total_site_heat_exchanger_network`, `pinch_design`, `thermal_derivative`, `network_evolution`, `optimise_duties`, `retrofit`, `retrofit_heat_pumps`, `design_basis`.
- `HeatExchangerNetworkDesignView` (`design.py`, in `__all__`): wraps one `HeatExchangerNetworkSynthesisResult`; `result`, `selected_network`, `top`, `network`, `grid`, `grid_layout`, `view`, `views`, `utility`, and the `total_heat_recovery`, `total_hot_utility`, `total_cold_utility` properties.
- `UtilityChoiceError` (`design.py`): `ValueError` raised when a bare heater or cooler needs a utility and the problem defines zero or several of that kind; carries `side` and `utilities`.
- `_PlotAccessorDescriptor` (`plot.py`): binds the presentation-owned `_PlotAccessor`, passing `select_hpr_graphs` from `OpenPinch/application/hpr_selection.py`.
- `_ComponentAccessorDescriptor` (`component.py`): binds `_ComponentAccessor` with `inventory` (read-only mapping) and `add_process_mvr`.
- Subdirectories: none.

## Invariants
- `heat_pump_and_refrigeration(cycle, duty, topology, placement, load, levels, cycle_options, search, ...)` (or `request=HprTargetRequest`) resolves the registered cycle, rejects an unavailable cycle (`NotImplementedError`, the named method's message when it has one), a duty or topology it lacks, and options for another cycle, then calls `_hpr` with the topology's model family and `spec.to_configuration(cycle_options)`. Screened refrigerants go to the matching named method's fluid-set runs. A run records the named method of its cycle and duty (`carnot_heat_pump` and so on) as its surface, or `heat_pump_and_refrigeration` for a cycle with none, with its cycle, duty, topology and placement under the `hpr_gateway` option, which the gateway reads back on replay. Screened refrigerants for a cycle with no named method are planned and run by the gateway itself [target.py:_TargetAccessor._gateway_fluid_set_runs]. Options given as a mapping are validated with the cycle's own options model, an invalid one raising `ValueError` that names the cycle. `hpr_cycles()` returns an `HprCycleCatalog` from the registry; it is not forwarded per period or per case [target.py:_TargetAccessor.heat_pump_and_refrigeration, _LEGACY_HPR_SURFACES].
- A Carnot target (`cycle="carnot"`, and so `carnot_heat_pump` and `carnot_refrigeration`) whose details leave one or more of two or more requested condenser or evaporator levels without duty (in every period, for a design shared by several: `hpr_details.period_outputs`) emits a `UserWarning` naming how many of each: the search stopped a level short of the best design for the levels asked for [target.py:_warn_of_idle_levels].
- A Carnot refrigeration target whose load serves less than 99.9 % of the cooling selected (`hpr_load.achieved` against `hpr_load.selected`) emits a `UserWarning` giving both and the share: a Carnot target serves what its model reaches and reports success, where a vapour compression refrigerator that cannot serve its duty raises [target.py:_warn_of_unserved_cooling].
- The seven named heat pump and refrigeration methods are wrappers that build the gateway's models; their targeting calls (surface, target, configuration, runtime options and service) are pinned by golden tests. The vapour compression wrappers normalise `simulation_backend` and run screened refrigerants before calling the gateway [target.py:_TargetAccessor.carnot_heat_pump].
- A recorded target run leaves out the options its method selects (those in `CONFIG_FIELD_SPECS` but not `USER_CONFIG_FIELD_SPECS`), so a replay can pass the rest back [target.py:_TargetAccessor._execute].
- Accessors are rebuilt per access and keep no cache; state lives on the `PinchProblem` [target.py:_TargetAccessorDescriptor] [design.py:_DesignAccessorDescriptor] [component.py:_ComponentAccessorDescriptor].
- Configuration keys in `options` are applied only for the duration of one call and then restored on every zone; keys that a descriptive method owns (in `CONFIG_FIELD_SPECS` but not user-settable) are rejected [target.py:_TargetAccessor._execute] [design.py:_DesignAccessor._run].
- The catalogue-generated `target.all_periods` forwarders reject `base_target`, `period_id`, and a non-positive-integer `workers`; each period solves on its own `snapshot_problem` copy and results are returned as deep copies [target.py:_AllPeriodsTargetAccessor._run]. `all_periods.utility_placement` rejects only `base_target` and runs one shared placement over every period; `all_periods.heat_recovery_dt_min` and `all_periods.hpr_load_kinks` run per period through `heat_recovery_dt_min.py` and `hpr_load_kinks.py` without populating `period_results` [target.py:_AllPeriodsTargetAccessor.utility_placement] [target.py:_AllPeriodsTargetAccessor.heat_recovery_dt_min] [target.py:_AllPeriodsTargetAccessor.hpr_load_kinks].
- Catalog forwarders never override methods defined explicitly in the class; `brayton_heat_pump`, `brayton_refrigeration`, `hpr_performance_map` and `hpr_refrigerant_screen` are excluded from `_AllPeriodsTargetAccessor` [target.py:install_catalog_forwarders call].
- Only one of `load_fraction`, `load_duty`, `period_loads` may be supplied to HPR methods [target.py:_load_options].
- `compressor_model` (vapour compression heat pump and refrigeration, MVR heat pump) and `mvr_compressor_model` (MVR heat pump) set `HPR_COMPRESSOR_MODEL` and `HPR_MVR_COMPRESSOR_MODEL` for one call; these arguments and a call's `options` take a compressor efficiency function, which stored options reject [target.py:_TargetAccessor.vapour_compression_heat_pump] [target.py:_TargetAccessor.mvr_heat_pump].
- `refrigerants` (vapour compression heat pump and refrigeration, MVR heat pump) sets `HPR_REFRIGERANTS` for a list or one fluid set and returns the target; a refrigerant screen result or layout instead runs the method once per proposed fluid set and returns an `HprFluidSetRunsResult` (single-stage and cascade layouts for a cascade cycle, parallel for a parallel cycle, VC+MVR for `mvr_heat_pump`, which then refuses `mvr_fluids` with `ValueError`) [target.py:_TargetAccessor._fluid_set_runs]. The cycle-specific `HPR_*` options and the screening layouts come from the cycle registry (`analysis/heat_pumps/cycles/registry.py`).
- On a problem holding a frozen HPR residual, `direct_heat_integration` (and `all_heat_integration`, which delegates to it) is the only transactional targeting surface that runs, and only without sub-zones or `options`; the others raise `ValueError` [target.py:_TargetAccessor._execute] [target.py:_TargetAccessor.all_heat_integration].
- `total_site_heat_integration` requires a zone of type `Site` [target.py:_TargetAccessor.total_site_heat_integration].
- `isentropic_cogeneration` requires `0 < efficiency <= 1` [target.py:_TargetAccessor.isentropic_cogeneration].
- Ranks are one-based positive integers; booleans are rejected [design.py:HeatExchangerNetworkDesignView.network] [design.py:HeatExchangerNetworkDesignView.top].
- A design run works on an isolated snapshot and commits it to the problem only after the service returns; the view holds a deep copy of the result [design.py:_DesignAccessor._run].
- `heat_exchanger_network` takes the search width and depth from the `width` and `depth` arguments, then the call's `options`, then the stored options. A width or depth given in the call, as an argument or in its `options`, also clears for that call the stored options its level governs, unless the call sets them; the design methods that take `**kwargs` (`pinch_design`, `thermal_derivative`, `network_evolution`) accept `width` and `depth` too [design.py:_DesignAccessor._arguments].
- `heat_exchanger_network` emits a `UserWarning` naming `total_site_heat_exchanger_network` when the master zone has more than one `Process Zone` subzone and no other `zone` is given, since it pools every process's streams [design.py:_DesignAccessor.heat_exchanger_network, _process_zones].
- `total_site_heat_exchanger_network` needs more than one `Process Zone` among the master zone's immediate subzones (else `ValueError`). It designs each twice with `heat_exchanger_network(zone=...)` at depth 0, with `HENS_UTILITY_PLACEMENT` `"price"` and `"temperature"`, `HENS_DESIGN_BASIS` `"all"` (on a multiperiod site each process is designed over every period at once, so its level duties hold per period and no fit to the periods follows), `HENS_OVERDESIGN_PERCENTAGE` `None` (rating at a margin would drop the level targets) and `HENS_PDM_MILP` as the call's depth resolves it, takes each run's first 50 ranked networks per process (a process whose design one way raises a `ValueError` or `RuntimeError` takes the other way's networks for both; when both raise, the error is raised, as is a missing synthesis solver or dependency), joins them into lowest-cost and level-held site seeds (`../../../analysis/heat_exchanger_networks/site/seeds.py:site_seeds`) and runs `network_evolution` on them with the call's width, depth and options, so no thermal derivative step runs, when its levels are `"given"` (`HENS_SITE_LEVELS`, the default) [design.py:_DesignAccessor.total_site_heat_exchanger_network, _site_design]. When that evolution raises `WorkflowContractError` (every task failed), the design returns the same choices of process networks joined whole (`site/seeds.py:joined_process_networks`), each costed by the site balance of its own utility use (`site/levels.py:priced_by_site_balance`), ranked and selected as any result, stored as the problem's design, with a `UserWarning` that the site evolution failed and nothing was refined across the site [design.py:_DesignAccessor._joined_process_design]. With `"given"` levels, `level_counts`, `placement` and `HENS_SITE_TIME_LIMIT` have no effect, and a `UserWarning` names each one that is set. With `levels="placed"` it hands the sweep over `level_counts` (`HENS_SITE_LEVEL_COUNTS`, validated as the option is) to `../../site_levels.py`, whose design for each count is the placed case's given-levels design with the call's width, depth and options, then refines the cheapest count by level moves (`../../site_level_moves.py:refine_selected`, `HENS_SITE_LEVEL_STEP` and `HENS_SITE_LEVEL_STEP_MIN`), each move designed by `network_evolution` on the shifted case from `move_seed` with the call's width, depth and options, and records the moves as `HENS_SITE_LEVEL_MOVES`; `levels` other than `"given"` or `"placed"` is a `ValueError` [design.py:_DesignAccessor.total_site_heat_exchanger_network].
- `total_site_heat_exchanger_network(heat_pump=..., heat_pump_cost=...)` resolves the call's configuration, multipliers (`resolve_search`) and costing as `heat_exchanger_network(heat_pump=...)` does and calls `design_with_heat_pump(..., placement="utility")` with its own arguments, so the heat pump heats and cools utility levels [design.py:_DesignAccessor.total_site_heat_exchanger_network].
- `pinch_design`, `thermal_derivative` and `network_evolution` design over every period and raise `ValueError` for a `period_id` (as an argument or in `options`) on a multiperiod case, naming `heat_exchanger_network(design_basis="period")` and `single_period_case` [design.py:_DesignAccessor._refuse_period_scope].
- `heat_exchanger_network` reads the basis and overdesign options (`HENS_DESIGN_BASIS`, `HENS_BASIS_*`, `HENS_OVERDESIGN_*`) from the call's `options` over the stored ones, applied as the run applies them [design.py:_DesignAccessor._effective_hens]. On a multiperiod case it resolves a design basis: `design_basis` if given, else `"period"` when `period_id` is given, else `HENS_DESIGN_BASIS` (default `"median"`). `"all"` with a `period_id`, `"period"` without one, and an unknown basis raise `ValueError`; on a single-period case the basis is ignored [design.py:_DesignAccessor._design_basis].
- `heat_exchanger_network(record=...)` runs into that `HeatExchangerNetworkRecord` (a new one when not given); the result's `ranked_networks` are exactly the record's entries and its first is selected. With no derived basis and no margin the synthesis service runs into it directly [design.py:_DesignAccessor.heat_exchanger_network] [../../../analysis/heat_exchanger_networks/service.py:heat_exchanger_network_open_hens_method_service].
- The `"period"` basis synthesises on `single_period_case(problem, period_id)` and the `"median"` basis on each candidate cluster's synthetic case (`HENS_BASIS_CANDIDATES`: the heaviest cluster, or every cluster), with the call's other arguments and no overdesign margin. Every network those syntheses admit is fitted (`_fit_to_all_periods`, with the call's options, solver and tolerance) and, with a margin, rated before it enters the call's record, through `_finalise_network`, the one fit and rating path. Within one call each fit is done once. A fit sets every duty and area afresh, so on a fitted basis networks share one fit, whatever duties they arrive with, when they agree in what the fit reads: every exchanger's kind, streams, stage and utility slice (the slice a heater's or cooler's id names; a unit idle in the basis case counts), the stage count, the design approach the fit holds, the level targets it holds and, for a network that holds levels, its dt_cont multiplier, at which the fit may target them again (`_fit_key`); with a margin and no fit, a rating keeps each network's own areas, so only a network offered again (from another task, so differing only in `task_id` and the `dt_cont_multiplier` summary metric, with the same design approach and values equal to 9 significant digits) reuses the first result (`_finalise_key`). Either way a later network takes the first one's result, or its failure; fits and ratings run one at a time under a lock, since a pooled run offers networks from its hand-off thread and the calling thread at once; a network whose fit or rating raises `ValueError` or `RuntimeError` (other than a missing solver or dependency) stays out, and `WorkflowContractError` is raised when none is left. So every cluster's networks join one record and the cheapest fitted network is selected. A fitted or rated network keeps what `_design_approach` reads of the network it was made from: its `method`, and in its `source_metadata` its `dt_cont_multiplier` and any recorded `min_exchanger_approach_share`, both also in its `summary_metrics`, so the network's JSON keeps them. `_design_approach` reads the multiplier from `summary_metrics`, else from `source_metadata`, and the share from `source_metadata`, else from `summary_metrics`. The fit and the rating are fixed-structure solves run as network evolution tasks, but they do not design the network, so a later rating holds the approach the network was designed to. The result is the selected network's fit (or rating) view; its provenance merges the basis synthesis's settings over the fit's: `design.heat_exchanger_network` over every period, with `HENS_DESIGN_BASIS` and `basis_period_id`, or `HENS_BASIS_CLUSTERS`, `basis_period_ids` and `basis_medoid`, in its settings [design.py:_DesignAccessor._design_finalised, _finalise_network, _design_on_derived_basis, _finalised_provenance].
- `heat_exchanger_network` on a problem (or zone) with only hot or only cold process streams designs over every period at once, whatever the design basis or `period_id`, since its heaters or coolers need no fit; an overdesign margin raises `ValueError` [design.py:_DesignAccessor.heat_exchanger_network].
- `heat_exchanger_network(zone=...)` resolves the zone (a name, an address or a `Zone`) as targeting does; for a zone other than the root it designs on `_zone_case(problem, zone)` (`case_derivation.py`), which holds that zone's streams with the problem's prepared utilities (defaults included, placed from the whole problem's temperatures, not the zone's) and keeps the zones above it, found by zone ancestry so a root name may contain "/", so stream keys match, and returns that case's view, so the problem's stored results are unchanged; a problem with process components is rejected [design.py:_DesignAccessor.heat_exchanger_network] [case_derivation.py:_zone_case].
- `heat_exchanger_network(overdesign_percentage=...)` (or `HENS_OVERDESIGN_PERCENTAGE`) validates the margin before synthesis, then rates every network (fitted first on a derived basis) with `apply_overdesign` through the `"rating"` objective at the approach the network's method designed it to (`_design_approach`: each exchanger's two stream contributions, at the network's dt_cont multiplier for a pinch design network and at that multiplier times the `HENS_MIN_EXCHANGER_APPROACH_SHARE` it was designed with, recorded in its `source_metadata` or else the configured one, for a thermal derivative or evolution network; each pair at least 0.1 K), not the 1 K rating default; a fitted network is rated at the floor its fit held (its `approach_temperature` summary metric: the design's floor, or 1 K after a fit that fell back) when it has one, so a fallback fit is not rated at an approach its areas cannot meet (`_finalise_network`); up to `HENS_OVERDESIGN_MAX`, before it enters the record (`_overdesigned`); the result keeps the synthesis provenance's method and settings, adds `HENS_OVERDESIGN_PERCENTAGE`, carries each network's metrics in its typed `overdesign` field (`NetworkOverdesign`, so it survives JSON) and is committed as the problem's design. `_apply_overdesign` rates one network the same way [design.py:_DesignAccessor._design_finalised, _overdesigned, _apply_overdesign].
- The median basis reads `to_problem_json()` with each stream's missing `heat_flow` filled from the prepared stream's per-period heat flow (matched in the stream's own zone by its full `<zone path>.<name>` key, so nested zones and same-named streams in different zones resolve), so streams given by heat capacity flowrate run [design.py:_DesignAccessor._median_basis, _with_prepared_heat_flows].
- `design_basis()` previews the median basis as a `HenDesignBasis` without synthesis; `basis_clusters` defaults to `HENS_BASIS_CLUSTERS`, and a cluster of one period warns when there are several clusters [design.py:_DesignAccessor.design_basis, _median_basis].
- `_fit_to_all_periods` (private) fits a network designed on one basis to every period: stream-end padding, then the `"cost"` objective, both at the approach the network was designed to (`_design_approach`: every network's own stream contributions through the request's `dt_cont_multiplier`, which is the network's dt_cont multiplier and, for a thermal derivative or evolution network, that multiplier times the `HENS_MIN_EXCHANGER_APPROACH_SHARE` it was designed with; each pair at least 0.1 K), so each exchanger gets one area over all periods and unused padding is removed; the padding holds each pair to the same contributions, the approach the fit holds. A network that holds its utility levels (`utility_level_targets`) is first fitted holding each level within a band of its target in every period (its own targets when they cover every period, else the case targeted at its dt_cont multiplier, `_period_level_targets`), with each held level's utility padded at every stream end it reaches. Each fit that raises `ValueError` or `RuntimeError` (not a missing solver or dependency) warns and gives way to the next: the levels are released, then the approach falls to 1 K. A fit or rating that does not hold the levels still records them as the network's `utility_level_targets`, so `holds_utility_levels` checks them (`_with_released_levels`). The cache keys of a fit (`_fit_key`) and of a rating alone (`_finalise_key`) hold the network's design approach (`_design_approach`) and level targets in place of its `dt_cont_multiplier` [design.py:_DesignAccessor._fit_to_all_periods, _design_approach, _period_level_targets, _optimise_duties, _with_released_levels, _finalise_key, _fit_key].
- `optimise_duties(objective="rating")` without a `min_approach_temperature` rates at the approach the network was designed to (`_design_approach`), as overdesign does, not 1 K; a mapping structure, of no method, keeps each exchanger's stream contributions [design.py:_DesignAccessor.optimise_duties].
- `_design_approach` reads a network's `approach_temperature` summary metric first: a network solved at one minimum approach on every exchanger (a duty optimisation or a retrofit given `min_approach_temperature`, a `"cost"` optimisation at its 1 K default, a fit that fell back to 1 K) is held to that approach by a later rating, overdesign, fit or retrofit, whatever multiplier it also records. The metric is the solve's `min_approach_temperature` only: `exchanger_approach_temperatures` given to that solve are not recorded on the network, so a later solve holds them only when they are given again [design.py:_DesignAccessor._design_approach].
- `optimise_duties`, `retrofit` and `retrofit_heat_pumps` refuse a site network with `ValueError`: one whose `source_metadata` has `site_utility_balance` or `site_processes` (a site seed), or whose `summary_metrics` has `site_total_annual_cost`. The fixed-structure model neither holds each process's levels nor keeps the site utility balance [design.py:_refuse_site_network].
- A design view's `total_heat_recovery`, `total_hot_utility` and `total_cold_utility` are the selected network's duties of that kind (kW); over several periods, their mean by each period's share of the year (`period_weights`, which the accessor passes from the problem; equal shares when not given). [design.py:HeatExchangerNetworkDesignView._total_duty]
- `retrofit` warns (`UserWarning`) when `heat_pump_cycle` is "carnot" and `heat_pump_cost` is 0: the machine then costs only its two exchangers.
- `retrofit` warns (`UserWarning`) when `HENS_FORBIDDEN_MATCHES` names any pair, in the problem's options or the call's: the retrofit search does not read the list, so a new match or a heat pump step may pair streams it names.
- A network given as a mapping carries no site metadata, so `retrofit` takes it; when its streams span several process zones the search proposes new matches only within one process and warns that the site utility balance is not modelled; with `HENS_RETROFIT_LOOPS` (default on) it may also link two processes through a new heat recovery loop, priced with `heat_recovery_loop_cost` [../../../analysis/heat_exchanger_networks/retrofit/search.py:run_retrofit_search].
- `optimise_duties` and `retrofit` mapping structures accept only the keys `recovery`, `heaters`, `coolers`, `hot_utility`, `cold_utility`, `stage_count`, and require `recovery`. An entry may be a mapping: recovery `hot`, `cold`, `stage`, heater or cooler `stream`, optional `utility` (the side's default otherwise) and `stage`, and on both optional `area` (the installed area) and `id` (the exchanger id); other keys raise `ValueError` [design.py:_DesignAccessor._network_from_structure, _recovery_entry, _utility_entry].
- `retrofit` runs `run_retrofit_search` on a snapshot of the problem under the call's configuration (`solver` sets `HENS_SOLVER_EVM`), with `new_unit_cost` defaulting to `COSTING_HX_UNIT_COST` and `min_approach_temperature` to `None` (each exchanger keeps the sum of its two sides' temperature contributions, per-stream `dt_cont` and zone multipliers included; the screens use twice `THERMAL_DT_CONT`; both are scaled by the multiplier `_design_approach` reads from the existing network, its dt_cont multiplier times its approach share for a thermal derivative or evolution network, passed as `RetrofitSettings.dt_cont_multiplier`, so a designed network is rated as it was designed; a network that records none, and any call with a `min_approach_temperature`, has 1; an existing network that records an `approach_temperature` is held to it as if it were the call's `min_approach_temperature`, and every network the search returns records what it was solved at, so a rating or second retrofit of it holds the same), a `UserWarning` when new units are priced but `area_addition_cost`, `split_cost` and `repiping_cost` are all 0, commits the snapshot's targets and returns the `HeatExchangerNetworkRetrofitResult`; the problem's cached design is not changed [design.py:_DesignAccessor.retrofit].
- `optimise_duties` and `retrofit` take a heat pump network (one whose `heat_pumps` carry `streams`) on the problem it was designed for: they build its case again (`heat_pump_network_case`) and solve there. `optimise_duties` returns that case's view; the problem's own stored design and targets are not changed. On any problem, the case itself included, `optimise_duties` of a network that records machines returns every network with them recorded and their annual cost in its total (`with_heat_pumps`). `retrofit` searches on a snapshot of the case; every design's network keeps the existing machines ahead of any its own heat pump step recorded, with their annual cost in its total, and every design's `utility_cost` includes the existing machines' electricity (savings are unchanged by it) [design.py:_DesignAccessor.optimise_duties, retrofit].
- `retrofit_heat_pumps` takes a network or, as `retrofit` does, a structure mapping (built by `_network_from_structure`).
- `optimise_duties`, `retrofit` and `retrofit_heat_pumps` read a mapping with `exchangers` as a network's JSON (`HeatExchangerNetwork.model_validate`, the form a design command returns through `run_command`) and any other mapping as a structure [design.py:_DesignAccessor._network_argument].
- `retrofit_heat_pumps` sets `HPR_TYPE` from `cycle` and `topology` through the cycle registry (`cycle_spec`, `family_value`; the cycle's default topology when `None`), applies `options` as configuration, passes `maximum_iterations` and `maximum_evaluations` as the HPR search budget, runs direct heat integration on a snapshot for the problem's first period unless that period's targets are cached, and calls `retrofit_heat_pumps` on it under that configuration; it commits the snapshot and restores the zones' configurations as `retrofit` does [design.py:_DesignAccessor.retrofit_heat_pumps].
- `inventory` returns a `MappingProxyType` copy of the process components [component.py:_ComponentAccessor.inventory].

## Side Effects
- Targeting methods mutate the owning problem: on success they commit the scratch zone tree, results, components and last run spec back to it; `target` methods record the run [target.py:_TargetAccessor._execute], `design` methods commit the snapshot and attach the synthesis result to `results.design` without recording [design.py:_DesignAccessor._run].
- The generated `target.all_periods` forwarders replace `_period_results`, `_period_states` and `_period_result_states` on the problem and may solve periods in a `ThreadPoolExecutor`, each in a copy of the caller's context so progress is reported to the caller [target.py:_AllPeriodsTargetAccessor._run].
- `design.heat_exchanger_network` on the `"all"` basis runs `target.all_periods.all_heat_integration()` first when the problem has no period results [design.py:_DesignAccessor._synthesise].
- `design.heat_exchanger_network` mutates the record it is given while it runs. On a derived basis or with a margin, each network's fit and ratings commit to the problem as they run (in a drain thread when synthesis runs in worker processes), and the selected network's result is committed last [design.py:_DesignAccessor._design_finalised].
- Lazy imports pull in analysis, presentation and optional synthesis code (Pyomo and the configured solvers, CoolProp-backed cycles) when a method is first called [design.py:_DesignAccessor.optimise_duties] [target.py:_TargetAccessor._hpr].
- `add_process_mvr` adds a component to the problem's `_process_components` through `create_process_mvr_component` [component.py:_ComponentAccessor.add_process_mvr].
- No file or network IO in this directory's own code; `design.*` methods run the HEN synthesis services, which launch external solvers through Pyomo [design.py:_DesignAccessor._run].
