# Problem accessors

## Overview
Private accessor namespaces that `PinchProblem` exposes as `target`, `design`, `plot` and `components`. Each is a non-data descriptor that builds a new accessor bound to the problem instance on every attribute access. The accessors hold no state of their own beyond the problem reference; they delegate to the targeting services, the HEN synthesis services, the presentation graph accessor and the process component factory. `OpenPinch/application/problem.py` imports the four descriptors; `OpenPinch/application/commands.py` imports `HeatExchangerNetworkDesignView` and `UtilityChoiceError`.

## Interface
- `_TargetAccessorDescriptor` (`target.py`): binds `_TargetAccessor`, the descriptive targeting workflows (direct, indirect and total-site integration, `all_heat_integration`, Carnot / vapour-compression / MVR heat pumps and refrigeration (`brayton_heat_pump` and `brayton_refrigeration` exist but raise `NotImplementedError`), Carnot and simulated ORC, area and cost, cogeneration variants, exergy, energy transfer, utility placement, `heat_recovery_dt_min`, `hpr_performance_map`).
- `_AllPeriodsTargetAccessor` (`target.py`): returned by `target.all_periods`; mirrors catalogued target methods once per canonical period, with a `workers` keyword; `utility_placement` and `heat_recovery_dt_min` are explicit methods. Its forwarders are generated by `install_catalog_forwarders`.
- `_DesignAccessorDescriptor` (`design.py`): binds `_DesignAccessor`: `heat_exchanger_network`, `enhanced_heat_exchanger_network`, `open_hens`, `pinch_design`, `thermal_derivative`, `network_evolution`, `optimise_duties`, `multiperiod_heat_exchanger_network`.
- `HeatExchangerNetworkDesignView` (`design.py`, in `__all__`): wraps one `HeatExchangerNetworkSynthesisResult`; `result`, `selected_network`, `top`, `network`, `grid`, `grid_layout`, `view`, `views`, `utility`, and the `total_heat_recovery`, `total_hot_utility`, `total_cold_utility` properties.
- `UtilityChoiceError` (`design.py`): `ValueError` raised when a bare heater or cooler needs a utility and the problem defines zero or several of that kind; carries `side` and `utilities`.
- `_PlotAccessorDescriptor` (`plot.py`): binds the presentation-owned `_PlotAccessor`, passing `select_hpr_graphs` from `OpenPinch/application/hpr_selection.py`.
- `_ComponentAccessorDescriptor` (`component.py`): binds `_ComponentAccessor` with `inventory` (read-only mapping) and `add_process_mvr`.
- Subdirectories: none.

## Invariants
- Accessors are rebuilt per access and keep no cache; state lives on the `PinchProblem` [target.py:_TargetAccessorDescriptor] [design.py:_DesignAccessorDescriptor] [component.py:_ComponentAccessorDescriptor].
- Configuration keys in `options` are applied only for the duration of one call and then restored on every zone; keys that a descriptive method owns (in `CONFIG_FIELD_SPECS` but not user-settable) are rejected [target.py:_TargetAccessor._execute] [design.py:_DesignAccessor._run].
- The catalogue-generated `target.all_periods` forwarders reject `base_target`, `period_id`, and a non-positive-integer `workers`; each period solves on its own `snapshot_problem` copy and results are returned as deep copies [target.py:_AllPeriodsTargetAccessor._run]. `all_periods.utility_placement` rejects only `base_target` and runs one shared placement over every period; `all_periods.heat_recovery_dt_min` runs the dt_min inversion per period through `heat_recovery_dt_min.py` [target.py:_AllPeriodsTargetAccessor.utility_placement] [target.py:_AllPeriodsTargetAccessor.heat_recovery_dt_min].
- Catalog forwarders never override methods defined explicitly in the class; `brayton_heat_pump`, `brayton_refrigeration` and `hpr_performance_map` are excluded from `_AllPeriodsTargetAccessor` [target.py:install_catalog_forwarders call].
- Only one of `load_fraction`, `load_duty`, `period_loads` may be supplied to HPR methods [target.py:_load_options].
- On a problem holding a frozen HPR residual, `direct_heat_integration` (and `all_heat_integration`, which delegates to it) is the only transactional targeting surface that runs, and only without sub-zones or `options`; the others raise `ValueError` [target.py:_TargetAccessor._execute] [target.py:_TargetAccessor.all_heat_integration].
- `total_site_heat_integration` requires a zone of type `Site` [target.py:_TargetAccessor.total_site_heat_integration].
- `isentropic_cogeneration` requires `0 < efficiency <= 1` [target.py:_TargetAccessor.isentropic_cogeneration].
- Ranks are one-based positive integers; booleans are rejected [design.py:HeatExchangerNetworkDesignView.network] [design.py:HeatExchangerNetworkDesignView.top].
- A design run works on an isolated snapshot and commits it to the problem only after the service returns; the view holds a deep copy of the result [design.py:_DesignAccessor._run].
- `heat_exchanger_network`, its multiperiod form and `enhanced_heat_exchanger_network` take the quality tier from the argument, then the call's `options`, then the option if the problem's stored options set it, then their own default (0, or 2 for `enhanced`); `open_hens` always runs tier 1 [design.py:_DesignAccessor._quality_tier].
- `multiperiod_heat_exchanger_network` needs existing all-period results (or `prerequisites=True`) and does not accept `period_id` [design.py:_DesignAccessor.multiperiod_heat_exchanger_network].
- `optimise_duties` mapping structures accept only the keys `recovery`, `heaters`, `coolers`, `hot_utility`, `cold_utility`, `stage_count`, and require `recovery` [design.py:_DesignAccessor._network_from_structure].
- `inventory` returns a `MappingProxyType` copy of the process components [component.py:_ComponentAccessor.inventory].

## Side Effects
- Targeting methods mutate the owning problem: on success they commit the scratch zone tree, results, components and last run spec back to it; `target` methods record the run [target.py:_TargetAccessor._execute], `design` methods commit the snapshot and attach the synthesis result to `results.design` without recording [design.py:_DesignAccessor._run].
- The generated `target.all_periods` forwarders replace `_period_results`, `_period_states` and `_period_result_states` on the problem and may solve periods in a `ThreadPoolExecutor`, each in a copy of the caller's context so progress is reported to the caller [target.py:_AllPeriodsTargetAccessor._run].
- `design.multiperiod_heat_exchanger_network` may run all-period targeting and overwrites the design provenance on the problem's results [design.py:_DesignAccessor.multiperiod_heat_exchanger_network].
- Lazy imports pull in analysis, presentation and optional synthesis code (GEKKO and the configured solvers, CoolProp-backed cycles) when a method is first called [design.py:_DesignAccessor.optimise_duties] [target.py:_TargetAccessor._hpr].
- `add_process_mvr` adds a component to the problem's `_process_components` through `create_process_mvr_component` [component.py:_ComponentAccessor.add_process_mvr].
- No file or network IO in this directory's own code; `design.*` methods run the HEN synthesis services, which launch external solvers through GEKKO [design.py:_DesignAccessor._run].
