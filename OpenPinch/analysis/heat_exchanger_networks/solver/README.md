# HEN Solver Support

## Overview
Everything between a prepared problem and the equation models: solver arrays built from the problem, piecewise thermal profiles for segmented streams, the PDM above/below-pinch decomposition, the native Pyomo model builder, Pyomo solver configuration, and optional-dependency guards. `../execution` calls these to build models; `../extraction` reads the arrays and profiles back when turning solutions into networks.

## Interface
- `problem_to_solver_arrays`, `PreparedSolverArrays`, `SEGMENT_PROFILE_VERSION`, `annual_cost_scales` (`arrays.py`): prepared-problem to padded, period-indexed arrays, axis maps, identities and unit conventions.
- `nominal_approach_temperature`, `ZERO_CONTRIBUTION_REPLACEMENT` (`arrays.py`): the internal scalar approach `2 * THERMAL_DT_CONT * m` of a synthesis task's dt_cont multiplier `m`, which the solver layer takes as its `dTmin` (it raises `ValueError` for a non-positive multiplier or `THERMAL_DT_CONT`), and the 0.1 K that replaces a zero contribution.
- `PiecewiseThermalProfile`, `profile_from_solver_arrays`, `branch_profile`, `branch_fractions`, `utility_thermal_profile`, `duty_aligned_area_contributions`, `add_piecewise_temperature_mapping`, `add_piecewise_cost_mapping`, `add_piecewise_temperature_contribution_mapping` (`piecewise.py`): segment profiles, duty-aligned area slices, and model constraints mapping duty to temperature, cost or contribution.
- `build_pinch_design_decomposition`, `PinchDesignDecomposition`, `PinchDesignTarget`, `PinchLocation`, `StageSelection` (`pinch_design_decomposition.py`): per-period pinch targets and clipped active-stream fields for the PDM.
- `with_utility_slices`, `with_named_slices`, `slice_label`, `slice_labels`, `slice_parent`, `sliced_decomposition`, `utility_slices`, `MINIMUM_SLICED_RANGE`, `MINIMUM_SLICE_SPAN` (`utility_slices.py`): arrays with each sliding utility cut into slices in series (or cut at the slices a network names), the slice a heater's or cooler's id names, a slice's parent, a decomposition on the sliced axes, and the slice-to-parent map.
- `SolverRun`, `cleanup_model_run_directory`, `require_solver_backend`, `stage_solver`, `FALLBACK_SOLVER`, `configure_pyomo_solver`, `solve_pyomo_model`, `PYOMO_SOLVERS`, `INTEGER_SOLVERS`, `PYOMO_SOLVER_MODULES`, `PYOMO_SOLVER_FACTORY_NAMES`, `SOLVE_TIME_OPTION_SOLVERS`, `DEFAULT_COUENNE_OPTIONS`, `DEFAULT_IPOPT_PYOMO_OPTIONS`, `DEFAULT_SOLVER_OPTIONS`, `CONVERGED_TERMINATION_CONDITIONS`, `PASSING_SOLVER_STATUSES`, `PASSING_TERMINATION_CONDITIONS`, `TIME_LIMIT_OPTIONS`, `WARM_START_SOLVERS`, `SOLUTION_FILE_SOLVERS`, `FEWEST_UNITS_TIME_LIMIT` (60 s, each fewest-units and minimum-unit solve), `PDM_TIME_LIMIT` (600 s, a pinch design side's first solve), `HEURISTIC_SIDE_TIME_LIMIT` (10 s, a heuristic side proposal's solve), `TDM_TIME_LIMIT` (300 s, a thermal derivative task's MINLP) (`backend.py`): solver selection, option files and normalised solves of native Pyomo models.
- `PyomoModel` (`pyomo_model.py`): a Pyomo `ConcreteModel` built through a small modelling interface (`Var`, `Param`, `Equation`, `Equations`, `Intermediate`, `sum`, `Minimize`, `Maximize`), so the HEN equation helpers build native Pyomo components. Every HEN model uses it. `import_duals()` adds an imported `dual` suffix and `dual(constraint)` reads a constraint's dual after a solve, `None` when duals were not imported or the solver reported none (Ipopt reports them).
- `require_synthesis_dependency`, `require_declared_synthesis_dependencies`, `require_solver_binary`, `SYNTHESIS_DEPENDENCIES`, `SynthesisDependency`, `SYNTHESIS_EXTRA`, `MissingSynthesisDependencyError`, `MissingSynthesisSolverError` (`dependencies.py`): optional package and executable guards.

## Invariants
- Arrays accept only a live prepared problem with a `Zone` master zone, a finite positive `dTmin`, and at least one hot and cold stream and utility [arrays.py:problem_to_solver_arrays].
- Units: temperatures K, heat capacity flowrate kW/K, HTC kW/m^2/K, utility price $/kW/y (price times `COSTING_ANNUAL_OP_TIME / 1000`), capital coefficients annualised by the capital recovery factor [arrays.py:annual_cost_scales, _solver_array_mapping].
- Stream and utility order follows input order; a default backup utility is dropped when real ones exist [arrays.py:_ordered_utility_items].
- Every stream, segment and utility contribution is its effective contribution (zone multiplier included) times the task's dt_cont multiplier `m = dTmin / (2 * THERMAL_DT_CONT)`, as targeting scales them, so `m = 1` gives the targeting contributions; a stream whose dt_cont multiplier is locked keeps its effective contribution. A contribution that is zero (at or below `tol`) after scaling becomes 0.1 K times `m` (0.1 K for a locked stream). The PDM decomposition bakes the same values into its copied zone [arrays.py:_temperature_contribution] [pinch_design_decomposition.py:_apply_hen_dt_cont_convention].
- `dTmin` is internal: synthesis results carry the dt_cont multiplier, never it [arrays.py:nominal_approach_temperature].
- Segmented parents carry a zero heat-capacity-flowrate sentinel; segment tensors are authoritative [arrays.py:_stream_heat_capacity_flowrate].
- A piecewise profile needs positive duties, CPs and HTCs, one direction and continuous temperatures [piecewise.py:PiecewiseThermalProfile.__post_init__].
- A split branch in an isothermal-mixing stage spans its stream's whole stage temperature change, so its share of the flow is its share of the stream's recovery duty in the stage (`branch_fractions`); its slices use the profile at that share (`branch_profile`) [piecewise.py:branch_fractions, branch_profile].
- Exchanger duty beyond a profile raises, except for solver noise within a relative allowance that is dropped [piecewise.py:duty_aligned_area_contributions].
- The PDM decomposition works on a deep copy of the master zone, and its stage boundary count satisfies `K = S + 1` [pinch_design_decomposition.py:_zone_with_hen_dt_contribution, PinchDesignDecomposition].
- Each `PinchDesignTarget` carries `hot_utility_level_targets` and `cold_utility_level_targets`: the duty (kW) the same direct-integration targeting assigns each utility in that period, at the task's contributions, in the decomposition's `hot_utility_identities` and `cold_utility_identities` order (the solver's utility axes); a utility targeting leaves unused, or one not on the axes, is 0 [pinch_design_decomposition.py:_level_targets].
- Utility slices: an unsegmented utility spanning more than `MINIMUM_SLICED_RANGE` (1 K) in every period is cut where a stream's supply plus its approach (stream and utility contributions) falls inside its range: a cold stream's for a hot utility, a hot stream's (less the approach) for a cold one. Cuts are shares of the range pooled over periods, merged when closer than `MINIMUM_SLICE_SPAN` (0.5 K) to each other or an end. Slices replace their parent on its axis, inlet first, named `<parent>@<inlet>-<outlet>` (degrees C, period 0), with every other per-utility value copied and the segment duty scaled by the share; `preparation["utility_slices"]` maps each side's slices to `[parent, share]`. With `like`, the cuts are another sliced array set's; with `cuts`, those. `with_named_slices` reads cuts back from slice labels (`<parent>@<inlet>-<outlet>`, degrees C, period 0, either end may be negative), so a network designed with slices gets the same slices; a label's parent is the longest utility name on the axis it starts with, then `@` (`slice_parent`), since names may hold `@`; a label that is itself a utility's name, names no utility, or has no numeric span makes no cut, nor does one spanning the whole utility. `slice_label` reads a candidate label from a synthesis heater or cooler id (`hot-utility:<utility>-><stream>`, `cold-utility:<stream>-><utility>`, `:S<stage>` for a staged unit) using the exchanger's own stream and stage, so names holding `->` or `:S` do not mislead, or takes the unit's utility name when it holds `@`. No cut returns the arrays themselves. `sliced_decomposition` gives each slice its parent's level target times its share [utility_slices.py:with_utility_slices, _cuts, sliced_decomposition].
- Shifted pinch temperature is the selected pinch (cold pinch when the hot utility target is zero, otherwise hot pinch) in K [pinch_design_decomposition.py:_shifted_pinch_temperature].
- A stream is active on a side of the pinch only if it reaches more than `tol` past its pinch temperature, so a stream that starts or ends at the pinch is not kept on the far side as a sliver [pinch_design_decomposition.py:_clip_stream_temperatures].
- Solver names must be in `PYOMO_SOLVERS` (`couenne`, `highs`, `ipopt-pyomo`, `scip`, `mindtpy`); any other name, including the removed `apopt` and `ipopt-GEKKO`, raises `MissingSynthesisSolverError` listing the supported names. Solver options are validated [backend.py:require_solver_backend, _normalise_solver_options].
- Pyomo solves that need an option file are serialised by a process-wide lock [backend.py:_solver_working_directory].
- `SolverRun.converged` is false for a solve that stopped at a termination condition outside `CONVERGED_TERMINATION_CONDITIONS` (an iteration or time limit, for example), though such a solve can still pass, and true when none was recorded [backend.py:SolverRun.converged].
- `PyomoModel(constraints=False)` holds values only: `Equation` returns `None` without adding a constraint and the objective is not set. [pyomo_model.py:PyomoModel]
- A `PyomoModel` has at most one objective; a second `Minimize` or `Maximize` raises `ValueError`. Its parameters are fixed variables, so they can be changed between solves. Variables and parameters come from preallocated blocks, a parameter block fixed as a whole when allocated, whose unused entries are in no constraint; the `PyomoModel.variables` list holds the variables handed out, in creation order. `Var`, `Param` and `Intermediate` take no name; `Intermediate` returns the expression itself; the Pyomo module is looked up once, when a model is made, and kept on the class so a model still pickles [pyomo_model.py:PyomoModel].
- A native Pyomo solve fails, with status 0, on a solver status outside `PASSING_SOLVER_STATUSES` or a termination condition outside `PASSING_TERMINATION_CONDITIONS` ("unbounded" and "noSolution" are outside it, as they carry no solution) or on an exception; otherwise its status is 1, values are loaded onto the variables and `objective_value` is the objective's value [backend.py:solve_pyomo_model].
- `configure_pyomo_solver` accepts only `PYOMO_SOLVERS` [backend.py:configure_pyomo_solver].
- `couenne` defaults to `feasibility_bt no`, `aggressive_fbbt no` and `optimality_bt no` under the given options, so every Couenne solve writes `couenne.opt` to the model's run directory [backend.py:DEFAULT_COUENNE_OPTIONS].
- `ipopt-pyomo` defaults to `bound_push` and `bound_frac` of 1e-6, `acceptable_tol` 1e-4, `acceptable_iter` 5 and `max_wall_time` 120 s under the given options (the last two need Ipopt 3.14 or later), and with `highs` takes its options at solve time (Ipopt on its command line), so neither writes an option file or takes the working-directory lock [backend.py:configure_pyomo_solver, solve_pyomo_model].
- `scip` needs the `pyscipopt` package and no executable and runs through Pyomo's `scip_direct`, quiet by default (`display/verblevel 0`). `mindtpy` runs Pyomo's MindtPy outer approximation with HiGHS masters and Ipopt subproblems, so it needs `highspy` and the `ipopt` executable, and takes its options (`DEFAULT_SOLVER_OPTIONS` under the given ones) as solve arguments. Both keep integers [backend.py:DEFAULT_SOLVER_OPTIONS, require_solver_backend, solve_pyomo_model].
- A solve that stops early, at a passing termination condition outside `CONVERGED_TERMINATION_CONDITIONS` or with status "aborted" (HiGHS at its time limit, for example), passes, unconverged, only with an incumbent: a returned solution or a finite best bound; without one it fails with status 0. `SOLUTION_FILE_SOLVERS` (`couenne`, `ipopt-pyomo`) are solved without loading, so their returned solution is seen before it is loaded. A `PyomoModel` with `warm_start` set starts HiGHS or SCIP from its current values; `TIME_LIMIT_OPTIONS` names each integer solver's time-limit option [backend.py:solve_pyomo_model, _has_incumbent].
- `highs` needs the `highspy` package and no executable; it runs in process through Pyomo's `appsi_highs` interface, takes its options at solve time and writes no option file. It rejects nonlinear models [backend.py:require_solver_backend, configure_pyomo_solver, solve_pyomo_model].

## Side Effects
- Pyomo solves with an option file (solver options supplied) change the process working directory under a per-process thread lock, restoring it afterwards [backend.py:_solver_working_directory].
- For a `PyomoModel` with Couenne options, creates a temporary run directory as the model's `_path` and writes `couenne.opt` into it [backend.py:configure_pyomo_solver, _write_solver_option_file].
- Deletes a model's run directory and recreates it, with its option file, on re-solve [backend.py:cleanup_model_run_directory, _restore_run_directory].
- Imports optional packages (`pyomo`, `openpinch_solvers`, `idaes`, `highspy`, `pyscipopt`) lazily. A solver executable is found on `PATH` first, then in the `openpinch_solvers` package (Ipopt) and then in the IDAES download. An `openpinch_solvers` directory is prepended to `PATH` and an IDAES one moved to its end, and looking up the IDAES directory restores the `PATH` that importing `idaes` changes, so IDAES's Ipopt never comes first on the `PATH` worker processes inherit. The IDAES directory an `idaes` import put first on `PATH` is also skipped in the `PATH` search, so it stays a fallback after `openpinch_solvers`. A `PATH` hit in this environment's scripts directory, where pip puts the `openpinch-solvers` launcher, is replaced by the `openpinch_solvers` executable when the package ships it, so solves do not start Python [dependencies.py:require_synthesis_dependency, require_solver_binary, _scripts_directory, _idaes_bin_directory, _path_without_imported_idaes, _prepend_path, _append_path].
- `stage_solver(solver_name, default=...)` returns `FALLBACK_SOLVER` (`scip`) when `solver_name` is its stage's default, whether left unset or set to it, and that solver's backend is missing while SCIP's is installed, emitting a `RuntimeWarning`; otherwise it returns `solver_name` unchanged, installed or not [backend.py:stage_solver].
- Launches solver executables, or HiGHS in process, through Pyomo. Ipopt and Couenne run the executable `configure_pyomo_solver` found, not whichever is first on `PATH` at solve time [backend.py:configure_pyomo_solver, solve_pyomo_model].
- `pyomo_model.py` imports `pyomo.environ` only when a `PyomoModel` is created or used [pyomo_model.py:_pyomo].
