# Heat Exchanger Network Analysis

## Overview
Heat exchanger network (HEN) synthesis, fixed-structure duty optimisation and controllability scoring. `service.py` dispatches the OpenHENS family of methods (pinch design, heuristic and MILP, thermal derivative, network evolution), `context.py` prepares settings and finalises the cached design, and the subpackages split planning, execution, extraction, reporting (including ranking), results, models, solver and targeting. Equation models live in `models`. The synthesis and duty-optimisation entry points are reached through `PinchProblem.design`; controllability is a standalone function.

## Interface
- `heat_exchanger_network_synthesis_service` and per-method `heat_exchanger_network_*_method_service` functions (`service.py`): dispatch one method and update the problem cache. The OpenHENS service takes `record=`, a `HeatExchangerNetworkRecord` (`results/record.py`) that receives every verified network as the run finds it.
- `prepare_service_context`, `finalise_design_result`, `ensure_target_results`, `normalise_runtime_options`, `optional_text` (`context.py`): shared service-boundary helpers.
- `heat_exchanger_network_duty_optimisation_service`, `build_duty_optimisation_request`, `DutyOptimisationRequest`, `fixed_network_structure`, `FixedNetworkStructure`, `FixedStructureDutyExecutor`, `build_solution_network`, `verify_solution` (not in `__all__`), `duty_optimisation_task`, `DUTY_OBJECTIVE_GOALS`, `DEFAULT_FEASIBILITY_APPROACH` (`duty_optimisation.py`): optimise exchanger duties on a user-defined network for `"utility"`, `"area"`, `"cost"` or `"rating"` (installed recovery areas).
- `apply_overdesign`, `validate_margin`, `with_scaled_recovery_areas`, `OPTIMISE` (`overdesign.py`): an overdesign margin on the recovery areas, rated over every period, fixed or optimised.
- `with_stream_end_utilities` (`period_fit.py`): a network designed on one basis, plus a heater or cooler at each stream end that has none, so a fit over every period can close each period's balance.
- `heat_pump_record`, `network_with_heat_pumps` (`heat_pump_cost.py`): a heat pump target priced as the machine a network records, and a network with its machines recorded, their electricity in its `utility_cost` and their annual cost (electricity and annualised capital) in its total (and in `summary_metrics["site_total_annual_cost"]` when it has one, the cost a site network ranks by).
- `is_one_sided`, `utility_only_network`, `utility_only_workflow`, `UTILITY_ONLY_TASK_ID` (`utility_only.py`): the network of a problem with only hot or only cold process streams: heaters or coolers alone at the targeted utility levels, built without a solver, and the one-task workflow result that holds it.
- `quantify_heat_exchanger_network_controllability` (`controllability.py`): 0 to 1 steady-state controllability score for a solved `HeatExchangerNetwork`, from an interaction matrix derived from exchanger duties.
- `PreparedProblem`, `SynthesisProblem` (`prepared_problem.py`): structural protocols for the problem state analysis code reads.
- `WorkflowContractError` (`errors.py`): raised when a synthesis workflow breaks its task contract or no task outcome succeeds.
- `build_index_grid`, `ordered_mapping_keys` (`indexing.py`): nested index grids, built in row-major order with one call per cell, and index-ordered mapping keys.
- Subdirectories:
  - [execution](./execution/README.md): settings, search levels, executors and task-builder helpers.
  - [extraction](./extraction/README.md): solved model to domain network.
  - [basis](./basis/README.md): the median design basis, clustered operating periods and their synthetic single-period case.
  - [heuristic](./heuristic/README.md): rules-based (Linnhoff) pinch design topology proposals.
  - [models](./models/README.md): concrete HEN equation models.
  - [reporting](./reporting/README.md): feasibility checks, ranking and exports.
  - [results](./results/README.md): result assembly, seeds and selection.
  - [retrofit](./retrofit/README.md): retrofit of an existing network, one modification at a time.
  - [site](./site/README.md): total site design: seeds from each process's networks and the site utility accounting.
  - [solver](./solver/README.md): solver arrays, piecewise profiles, backends and dependency guards.
  - [targeting](./targeting/README.md): method orchestration and topology helpers.

## Invariants
- Runtime options reaching this package must be a dict or `None` and must not contain `HENS_` keys; persistent controls are loaded with the problem. The `problem.design` accessors move `HENS_` keys from a call's `options` into that call's configuration before this check, so users may pass them there [context.py:normalise_runtime_options].
- Open-HENS and PDM reject `initial_networks`, and the heuristic pinch design method is not a method of its own (PDM runs it); `method=None` and `OpenHENS` run the full workflow at the configured search width and depth [service.py:heat_exchanger_network_synthesis_service].
- An accepted design is ranked, selected and verified; verification failures raise `RuntimeError` [context.py:finalise_design_result].
- The OpenHENS service runs inside `running(record)` (a new record when none is given), so the record is `complete` with the selected entry marked when the result is returned, `failed` when the run raises, and the result ranks exactly its entries [service.py:heat_exchanger_network_open_hens_method_service] [results/record.py:running].
- A utility-only network gives each utility level the duty targeting's own algorithm assigns it (`_calculate_assigned_utility_duties`) on the composite curve in shifted temperatures, with every utility level a row, at the targeting contributions (dt_cont multiplier 1). Levels are cut from the pinch end (the cold end for heaters, the hot end for coolers) in targeting's order, least valuable first and a default utility last; each stream's heat between two cuts goes to that level, so a stream spanning levels has utility exchangers in series, one per (utility, stream). Exchanger area is the sum of duty-aligned slices; capital is `COSTING_HX_UNIT_COST` per unit plus `COSTING_HX_AREA_COEFF * area ** COSTING_HX_AREA_EXP`, annualised; utility cost is each level's duty at its price, period-weighted. Segmented utilities raise `ValueError` [utility_only.py:utility_only_network].
- A heat pump's record prices electricity as the target's work times `COSTING_HPR_ELE_PRICE` ($/MWh) times `COSTING_ANNUAL_OP_TIME` / 1000, and capital as a cost per kW of condenser capacity (compressor and motor; the condenser and evaporator are exchangers of the network) annualised at the capital recovery factor of `COSTING_DISCOUNT_RATE` and `COSTING_SERVICE_LIFE`. Its `load_fraction` is the target's selected load over its available load (`hpr_load`), or `None` without that summary. With `period_weights` and a target that holds period outputs (a shared design), the work is the period-weighted mean of each period's `w_net` (and the electricity is priced on it), the COP is the weighted condenser heat over that work, and the condenser and evaporator duties are the largest of any period, on which the capital is sized. A period with no output, or whose output has no condenser duty, is one the machine is off in: it adds no work and no heat and keeps its weight. `network_with_heat_pumps` returns a copy whose `total_annual_cost` is the network's plus each machine's `annual_cost`; `utility_cost` is the network's utilities plus each machine's `electricity_cost`, and `capital_cost` stays the network's own exchangers [heat_pump_cost.py:heat_pump_record, network_with_heat_pumps].
- A utility-only workflow raises `ValueError` naming the pairs when its one network uses a pair `HENS_FORBIDDEN_MATCHES` names: the levels are targeting's, so there is no other network to return [utility_only.py:utility_only_workflow].
- Analysis code accepts the `PreparedProblem` protocol instead of importing the application layer [prepared_problem.py:PreparedProblem].
- Duty optimisation: `"area"` needs a utility cap, `"cost"` and `"utility"` reject caps, and every process stream needs at least one exchanger, checked at solve time (including after each idle-exchanger removal) so a violation surfaces as a failed task and `WorkflowContractError` from the service [duty_optimisation.py:build_duty_optimisation_request] [duty_optimisation.py:_require_every_stream_served].
- Overdesign scales recovery areas only, by `1 + OD/100`; heaters and coolers keep their design areas. `"optimise"` rates both ends of `[0, maximum]` and then runs a bounded `minimize_scalar` search (0.5 point tolerance, at most 15 more solves), choosing the cheapest point evaluated, a tie to the smaller margin. The rating at 0 % must succeed; a positive margin whose rating raises `ValueError` or `RuntimeError` (not a missing solver or dependency) counts as infinite cost and is left out of the points; after a failed maximum, bisection (to the 0.5 point tolerance) finds the largest margin that rates, which bounds the search; when no positive margin was rated the margin is 0 % with a `UserWarning`. The metrics hold mode, percentage, each period's recovery and utility before and after, the cost at 0 and at the margin, every `[percentage, cost]` point, and the failed margins (`failed_margins`) [overdesign.py:apply_overdesign].
- The `"rating"` objective needs a positive `area` on every exchanger and rejects utility caps. Each exchanger's design point per solver period (matched by period id: duty, end approaches, recorded or else from its inlet and outlet temperatures, and its slice area when segmented) lets the model scale its capacity so the installed area carries its design duty; a rated segmented exchanger keeps its installed area [duty_optimisation.py:build_duty_optimisation_request, _design_points, build_solution_network].
- Duty optimisation runs several heaters (or coolers) at one position of a stream in series, coldest heater (warmest cooler) first. Synthesis reports several stream-end heaters on one stream as a parallel split (`../extraction/service.py:_end_utilities_in_parallel`), so a fit to every period, a rating or an overdesign of such a network re-solves them in series, over different temperature spans [models/fixed_structure.py:utility_chains].
- A rated network is verified with each unit's rating allowance (`rating_allowances`: how much more area exact sizing needs than the cap's design-calibrated Chen LMTD), recorded per exchanger in `source_metadata["rating_area_allowances"]` and as the largest in `summary_metrics["rating_area_allowance"]`; its reported areas stay as installed [duty_optimisation.py:FixedStructureDutyExecutor._solve, _with_allowances].
- A rating holds every exchanger to `DEFAULT_FEASIBILITY_APPROACH` (1 K) in every period unless an approach is given. A fit to every period (`problem_approach`) holds each exchanger to its streams' dt_cont contributions, the design's minimum approach; only when that fit fails does it warn and fit at 1 K, so a fitted network sits below the design's minimum only after that warning [duty_optimisation.py:build_duty_optimisation_request] [../../application/_problem/accessors/design.py:_DesignAccessor._fit_to_all_periods].
- Duty optimisation cuts its arrays at the utility slices the network's heater and cooler ids name (`with_named_slices`), runs each such unit on its slice, and reports it under the parent utility, as synthesis does; before, a slice ran over its parent's whole range, and a slice only it could reach was rejected [duty_optimisation.py:FixedStructureDutyExecutor._solve, fixed_network_structure, build_solution_network].
- `level_targets` on a duty optimisation request (utility name to per-period duty) holds the heaters (by source) or coolers (by sink) of each named utility at its target in every period; a level with a non-zero target and no exchanger raises `ValueError`, and the solved network records the targets as `source_metadata["utility_level_targets"]` [duty_optimisation.py:_level_holds, build_solution_network].
- Stream-end padding holds each stream and utility to `approach` when given (a floor), else to the pair's own dt_cont contributions (a process stream's largest segment contribution; a utility's inlet segment contribution at its inlet and its outlet segment contribution at its outlet) times `dt_cont_multiplier`, the approach a fit at that multiplier holds. It first drops any end utility of the network that cannot keep that approach at both ends in every period its stream runs (has a heat capacity flowrate or, for a segmented stream, segment duty), then gives each stream with no end utility the cheapest utility (period-weighted price) that can; a stream no utility reaches gets none, and staged utilities and recovery exchangers are kept; a heater or cooler whose id names a utility slice keeps that slice (the padding arrays are cut at the network's slices); with `levels`, every utility named there is also placed at each stream end it can serve, so a held level has exchangers to carry its target [period_fit.py:with_stream_end_utilities].
- Stream-end padding offers no pair that `HENS_FORBIDDEN_MATCHES` names and drops an end utility of the network that it forbids, as it drops one that cannot reach [period_fit.py:with_stream_end_utilities].
- Exchangers left at zero duty in every period are removed one per pass, the idle one with the smallest `max_duty` first, and the allocation is re-solved until none are idle [duty_optimisation.py:FixedStructureDutyExecutor._solve].
- A solve that fails is tried once more with each recovery exchanger held idle in the periods the given network idles it in (`fixed_network_structure(hold_idle=True)`: an exchanger with duty in one period and none in another; a bare structure has none), when there is such a period. The solved network then records `summary_metrics["idle_periods_held"]`, the exchanger-periods held. A failed solve with nothing to hold fails as before [duty_optimisation.py:FixedStructureDutyExecutor._solve, _idle_periods].
- A solve that stopped at a solver limit (`solver_run.converged` false) records `diagnostics["unconverged_termination"]` on its outcome, verified or not. A verified one stays a success and the service raises a `UserWarning` naming the termination; one that fails verification fails with an error naming it. Only a termination in `LIMIT_TERMINATION_CONDITIONS` (an iteration, evaluation or time limit) adds the advice to raise `max_iter` or `max_wall_time` in `HENS_SOLVER_OPTIONS_EVM`, which the service's `WorkflowContractError` repeats; another (`minStepLength`, say) is named without it. This covers `optimise_duties`, the fit to every period and overdesign ratings, which all run through the service [duty_optimisation.py:FixedStructureDutyExecutor._solve, _warn_if_unconverged] [results/assembly.py:demote_infeasible_outcomes].
- The numeric controllability options are validated, component scores lie in 0 to 1, and the composite uses fixed weights renormalised over the components that are not `None` [controllability.py:_validate_options, _COMPOSITE_WEIGHTS].

## Side Effects
- `finalise_design_result` assigns `problem._results` with the design attached [context.py:finalise_design_result].
- `ensure_target_results` runs direct heat integration through `problem.target` when no matching targets are cached [context.py:ensure_target_results].
- Synthesis runs solver models in a `ProcessPoolExecutor` through `LocalSynthesisExecutor` when more than one worker is available and the main script has a main guard (or the start method is fork); duty optimisation solves serially in-process through `FixedStructureDutyExecutor`. Both launch external solver executables via Pyomo [execution/executor.py:LocalSynthesisExecutor, duty_optimisation.py:FixedStructureDutyExecutor].
- Controllability and indexing are pure.
