# HPR and MVR Notebook Reliability Tech Stack Decisions

## Retained Stack

| Concern | Decision | Rationale |
|---|---|---|
| Notebook format | Jupyter notebook v4 JSON generated by the existing script | Preserves package-resource and tutorial contracts. |
| Authoring | `scripts/generate_tutorial_notebooks.py` | Keeps one source of truth and supports deterministic regeneration. |
| Workflow API | Public `PinchProblem` target and component accessors | Existing scalar, multiperiod, performance-map, and process-MVR contracts satisfy the requirements. |
| Thermodynamics | Existing CoolProp backend; TESPy remains optional | Matches current declared dependencies and avoids compatibility fallback. |
| Optimization | Existing OpenPinch optimizer adapters with explicit public hard caps | No new algorithm or backend is needed for the verified bounded solves. |
| Contracts | Existing Pydantic HPR result, simulation-record, and failure-summary models | They already provide detached JSON-mode data and bounded diagnostics. |
| Static notebook validation | Existing `json`, `ast`, `nbformat`, and packaging tests | Covers syntax, source-only state, format validity, and generator drift. |
| Example and integration tests | pytest | Existing repository execution and marker/profile conventions remain authoritative. |
| Property tests | Hypothesis | Already installed and required by the enabled Property-Based Testing extension. |
| Quality gates | Existing Ruff, documentation, packaging, and broad pytest commands | Avoids a second lint or notebook-test framework. |

## Rejected Additions

- **Papermill, nbclient, or a new notebook runner**: rejected because the current
  code-cell execution harness is sufficient and easier to attribute by
  parameterizing notebook names.
- **A production notebook-summary service**: rejected because compact
  presentation is tutorial-local and does not justify a public API.
- **A second property-testing library**: rejected because Hypothesis already
  satisfies the requirement.
- **A wall-clock timeout dependency**: rejected because explicit optimizer
  iteration/evaluation caps are deterministic and cross-platform; elapsed time
  remains recorded diagnostic evidence.
- **Infrastructure or monitoring tools**: rejected because execution is local
  and opt-in.

## Compatibility Decisions

- Keep optional TESPy behavior feature-gated and distinct from CoolProp.
- Preserve existing public exception and result contracts.
- Do not import private `OpenPinch.analysis`, `application`, `domain`, or
  presentation owners from notebooks.
- Keep all checked-in generated notebooks source-only and compatible with the
  existing package resource copier.
- Use standard JSON serialization for diagnostic properties and summaries.

## Extension Compliance

- Property-Based Testing: Hypothesis retained; no new dependency required.
- Security Baseline: disabled; no security stack decision required.
- Resiliency Baseline: disabled; no resiliency framework required.
