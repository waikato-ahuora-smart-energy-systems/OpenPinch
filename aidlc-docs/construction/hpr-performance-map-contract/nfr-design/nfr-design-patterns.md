# Unit 1 NFR Design Patterns

## Pattern overview

Unit 1 applies local library patterns only. It adds no network service,
database, cache, message queue, background worker, retry loop, or deployment
component.

## NFRP-001: Strict immutable boundary

All public contract values share one frozen, extra-forbidding, non-finite-
rejecting base configuration. Field types describe the accepted data domain;
cross-field rules refine it. Successful construction produces an immutable
canonical value.

**Satisfies**: NFR-U1-001 through NFR-U1-003, NFR-U1-007, NFR-U1-013 through
NFR-U1-015.

**Failure behavior**: reject at construction with the precise field or model
location. Do not create a partially usable map and do not mutate source input.

## NFRP-002: Layered fail-fast validation

Validation executes in this order:

1. shape, required/extra fields, and primitive types;
2. finite/range, identity, enum, and exact-unit rules;
3. recursive JSON provenance rules;
4. point-level energy, capacity, and COP rules;
5. curve grouping, fixed-temperature, ordering, and uniqueness rules; and
6. map-level mode/convention and deterministic-order rules.

Later layers may assume earlier invariants. Errors retain the failing layer's
location and invariant-focused message. No retry or fallback is used because
the same deterministic input would fail identically.

**Satisfies**: NFR-U1-002, NFR-U1-007, NFR-U1-009, NFR-U1-013.

## NFRP-003: Linear index-and-group validation

One scan builds:

- a set of point names;
- a set of coordinate tuples; and
- a dictionary from `curve_id` to its ordered point list.

Each grouped curve is then scanned once. Provenance is traversed once
recursively. No validator performs all-pairs comparison or repeatedly searches
the complete point collection.

**Satisfies**: NFR-U1-004 and NFR-U1-006.

**Verification**: code review of the loop/index structure plus a deterministic
10,000-point validation case with a 2.0-second ceiling.

## NFRP-004: Canonical value normalization

Request coordinate sets are normalized to ascending immutable tuples after
duplicate and finiteness checks. Map points must already satisfy the documented
global order; invalid order fails rather than being silently rearranged at the
external payload boundary. Producer helpers construct points in canonical
order.

This distinction preserves error detection for malformed consumer payloads
while making equivalent generation requests order-independent.

**Satisfies**: NFR-U1-002, NFR-U1-008, NFR-U1-018.

## NFRP-005: Detached data-only serialization

Mapping and JSON serialization recursively creates plain detached values.
Returned lists and dictionaries do not share mutable containers with contract
state. The decoder accepts only the declared JSON domain and never invokes
dynamic imports, executable hooks, pickle, or object stringification.

**Satisfies**: NFR-U1-010, NFR-U1-012 through NFR-U1-014.

## NFRP-006: One authoritative model, generated resources

The map contract is the source for JSON Schema. Valid contract instances are the
source for the heat-pump and refrigeration fixtures. One deterministic generator
creates canonical text for all three resources and supports:

- check mode: compare generated bytes with committed resources and fail on
  drift; and
- explicit write mode: update only the three resolved package-resource targets.

No application import or package import writes files.

**Satisfies**: NFR-U1-008, NFR-U1-015, NFR-U1-019.

## NFRP-007: Canonical JSON text

The resource generator applies UTF-8, sorted object keys, two-space indentation,
non-ASCII preservation, array-order preservation, and one trailing newline.
The same function formats schema and fixture content.

**Satisfies**: NFR-U1-008, NFR-U1-015, NFR-U1-019.

**Verification**: repeat generation in separate processes and require
byte-identical results.

## NFRP-008: Package-resource abstraction

Runtime reads use `importlib.resources` against the importable resource package.
Callers may request a schema or named fixture through a closed catalog. The
reader returns immutable text/bytes or a newly parsed detached mapping and never
exposes a checkout-relative path as its primary contract.

**Satisfies**: NFR-U1-005, NFR-U1-006, NFR-U1-018, NFR-U1-019.

## NFRP-009: Dependency firewall

The contract/resource dependency direction is:

- Python standard library and Pydantic into the contract module;
- the contract module into the explicit development resource generator;
- standard `importlib.resources` into the resource reader; and
- pytest, Hypothesis, and `jsonschema` into tests only.

CoolProp, TESPy, existing runtime HPR target contracts, OpenUtility, Pyomo, and
HiGHS have no inward import edge. A subprocess test blocks optional TESPy and
external optimizer imports and imports/uses Unit 1. A static test separately
inspects Unit 1 source for forbidden direct imports, including CoolProp.

**Satisfies**: NFR-U1-003, NFR-U1-005, NFR-U1-010 through NFR-U1-012.

## NFRP-010: Dual independent conformance

Every golden fixture must pass two paths:

1. OpenPinch model validation and round-trip equality; and
2. development-only `jsonschema` validation of the parsed plain JSON against
   the committed schema.

The JSON Schema path is an independent structural oracle. Semantic business
rules that JSON Schema cannot fully express remain verified by the authoritative
contract and explicit/property tests.

**Satisfies**: NFR-U1-002, NFR-U1-011, NFR-U1-015 through NFR-U1-017.

## NFRP-011: Complementary deterministic test pyramid

Testing is divided into:

- exact examples for the two golden fixtures and every validation category;
- Hypothesis properties for round trips, detachment, ordering, physical rules,
  and request permutation equivalence;
- architecture tests for import/dependency boundaries;
- a coarse generated performance regression;
- package inventory and installed-wheel resource smokes; and
- an external data-only OpenUtility fixture test maintained downstream.

Hypothesis uses reusable valid-domain strategies, normal shrinking, and the
repository seed/replay policy. A minimized found defect becomes an exact
regression.

PBT-08 is realized by preserving shrinking and replayable seeds. PBT-09 is
realized by the existing Hypothesis/pytest integration selected in NFR
Requirements.

**Satisfies**: NFR-U1-016, NFR-U1-017, NFR-U1-020 and PBT-02, PBT-03, PBT-05,
PBT-07 through PBT-10. PBT-04 and PBT-06 remain N/A.

## NFRP-012: Quality-gate layering

Gates run from cheapest to broadest:

1. focused Unit 1 examples and properties;
2. contract and architecture regressions;
3. Ruff lint/format and patch hygiene;
4. warning-strict documentation;
5. source/wheel build and package validation;
6. dependency audit; and
7. isolated installed-wheel resource smoke.

Dependent units cannot consume a failing Unit 1 contract. Build and Test repeats
the broad gates after all three units integrate.

**Satisfies**: NFR-U1-003, NFR-U1-016 through NFR-U1-020.

## Resilience, availability, and security disposition

- **Retries**: N/A. Validation is deterministic and local; retries would hide
  no transient failure.
- **Fallback/default coercion**: prohibited for version, units, modes,
  conventions, invalid points, provenance, and resources.
- **Availability/failover**: N/A. There is no service state or remote dependency.
- **Recovery**: correct the input or restore generated resources from source
  control; no runtime recovery workflow is required.
- **Security**: closed data validation, no executable deserialization, and no
  dynamic imports address Unit 1's ordinary safety boundary. Security Baseline
  remains disabled.
- **Resiliency extension**: disabled; the fail-fast reliability requirements
  above are ordinary Unit 1 design, not extension enforcement.

## Pattern coverage validation

NFRP-001 through NFRP-012 collectively cover NFR-U1-001 through NFR-U1-020.
No pattern introduces infrastructure, persistence, runtime engine coupling, or
an external consumer dependency.
