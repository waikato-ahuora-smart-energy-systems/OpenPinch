# Unit 1 Technology-Stack Decisions

## Decision summary

| Concern | Decision | Rationale |
|---|---|---|
| Runtime language | Existing Python `>=3.14.2` | Matches the package baseline and needs no compatibility layer |
| Contract framework | Existing Pydantic 2 (`pydantic<3`) | Strict frozen values, cross-field validation, JSON/schema support, established repository pattern |
| JSON encoding | Python standard-library `json` plus Pydantic JSON-mode dumps | Data-only, portable, deterministic formatting without a runtime dependency |
| Resource access | `importlib.resources` | Works from checkout, wheel, and source distribution without filesystem assumptions |
| Schema generation | Pydantic `model_json_schema()` from the authoritative map model | Prevents a hand-maintained duplicate shape |
| Independent schema test | Development-only `jsonschema` | Verifies that plain fixture JSON conforms without importing OpenPinch models |
| Example tests | Existing pytest | Repository-standard focused and regression execution |
| Property tests | Existing Hypothesis integrated with pytest | Required PBT-09 features: domain strategies, shrinking, reproducible seeds |
| Build/package | Existing Hatchling and `python -m build` workflow | Automatically packages resources within the OpenPinch package |
| Style/static checks | Existing Ruff configuration | Consistent Python 3.14 lint and formatting gate |

## Contract module

The authoritative specialist module is
`OpenPinch.contracts.hpr_performance_map`. It uses a small frozen base model with
strict extra-field rejection and non-finite-number rejection. Literal values
represent the closed schema version, mode-linked conventions, and interpolation
topology. Cross-field validation owns physical and curve invariants.

The module does not import existing runtime HPR contracts because those values
permit arbitrary engine/domain types and have different semantics. It also does
not import NumPy, Pandas, Pint, CoolProp, TESPy, OpenUtility, Pyomo, or HiGHS.

No new symbol is exported from package root `OpenPinch`. Direct specialist
imports remain available from `OpenPinch.contracts.hpr_performance_map`; the
otherwise empty `OpenPinch.contracts` namespace need not become an aggregate
re-export owner.

## Recursive JSON provenance

The contract defines an explicit recursive `JsonValue` type covering null,
boolean, string, finite number, list, and string-keyed object values. Pydantic
validation is supplemented by one recursive finiteness/key validator so JSON
types retain their identity and unsupported runtime objects are rejected rather
than converted.

The design deliberately avoids generic `Any` as the public provenance value
contract and avoids custom arbitrary-type encoders.

## Deterministic JSON policy

Canonical resource JSON uses UTF-8, `ensure_ascii=False`, two-space indentation,
sorted object keys, compact standard separators consistent with indentation,
and exactly one trailing newline. Point order is already canonical in the map;
JSON encoding does not reorder arrays.

Runtime `model_dump(mode="json")` remains the ordinary typed-to-plain mapping
operation. A Unit 1 resource-generation helper applies the canonical text policy
for schema and golden files. It compares generated bytes with committed bytes
in check mode and writes only in explicit regeneration mode.

## Resource layout

The published resources live below the package at:

- `OpenPinch/data/contracts/hpr_performance_map/schema-1.0.json`;
- `OpenPinch/data/contracts/hpr_performance_map/heat-pump-1.0.json`; and
- `OpenPinch/data/contracts/hpr_performance_map/refrigeration-1.0.json`.

That directory is an importable package resource. A narrow resource helper
returns detached parsed JSON or immutable text/bytes and uses
`importlib.resources`, never a checkout-relative `Path` assumption.

## JSON Schema conformance

Pydantic generates the schema from `HprPerformanceMap`. The committed schema is
canonicalized with the same JSON policy as fixtures. Tests use development-only
`jsonschema` to:

- validate the schema document against its declared meta-schema;
- validate both parsed fixtures against the committed schema; and
- prove an independent plain-JSON path without instantiating OpenPinch models.

`jsonschema` is declared directly in the development dependency group if it is
not already direct. It is not added to runtime dependencies or optional HPR
extras.

## Testing framework and organization

- `tests/contracts/test_hpr_performance_map.py` owns explicit valid/invalid
  examples, field semantics, detachment, schema, and resource behavior.
- `tests/contracts/test_hpr_performance_map_properties.py` owns Hypothesis
  round-trip and invariant properties.
- `tests/strategies/hpr_performance_maps.py` owns reusable constrained request,
  point, provenance, and complete map strategies.
- `tests/architecture/` owns blocked-engine and forbidden-import checks.
- package/distribution tests own wheel/source resource presence and installed
  smoke behavior.

Hypothesis uses existing pytest integration and repository fixed-seed/replay
practice. Automatic shrinking stays enabled. Generated values are domain
objects or structurally valid payloads, not unconstrained primitives.

## Performance approach

Validation uses dictionaries/sets keyed by point name, curve identifier, and
coordinate tuple. It performs a single map scan plus one scan per grouped curve,
preserving `O(points + provenance_values)` time and memory. No pairwise distance
matrix, DataFrame, array copy, network call, or engine calculation is permitted.

The 10,000-point performance regression uses a deterministic generated valid map
and a coarse 2.0-second ceiling to detect accidental superlinear behavior. It is
not a micro-optimization benchmark and does not justify adding a faster JSON or
array library.

## Rejected alternatives

| Alternative | Decision | Reason |
|---|---|---|
| Reuse `HeatPumpTargetOutputs` or `HPRBackendResult` | Reject | Runtime/domain artifacts and permissive arbitrary types violate the plain contract |
| Plain dataclasses only | Reject | Would duplicate strict parsing, error locations, JSON, and schema machinery already standardized on Pydantic |
| Hand-maintained JSON Schema | Reject | High drift risk from the authoritative model |
| Add `jsonschema` at runtime | Reject | Independent validation is a development/consumer concern, not runtime behavior |
| NumPy arrays or Pandas frames | Reject | Not JSON-native and unnecessary for linear contract validation |
| Pint quantities in serialized values | Reject | Schema requires explicit canonical unit labels and plain numbers |
| `orjson` or another encoder | Reject | No measured need; adds runtime/platform surface |
| Import OpenUtility contract classes | Reject | Reverses the intended data-only package boundary |
| Put TESPy in Unit 1 | Reject | Violates engine-independent cold imports and unit ownership |
| Add root `OpenPinch` exports | Reject | The specialist contract does not need to expand the primary workflow facade |

## NFR and extension traceability

- Pydantic and standard JSON/resources satisfy NFR-U1-001 through NFR-U1-003,
  NFR-U1-007 through NFR-U1-015, and NFR-U1-018 through NFR-U1-019.
- Linear validators and the focused generated performance case satisfy
  NFR-U1-004 through NFR-U1-006.
- pytest, Hypothesis, `jsonschema`, Ruff, Hatchling, and distribution checks
  satisfy NFR-U1-016, NFR-U1-017, and NFR-U1-020.
- Hypothesis is the selected PBT-09 framework; PBT-08 shrinking and seed
  reproducibility are retained. No PBT NFR finding is blocking.
- Security Baseline and Resiliency Baseline are disabled; no technology is added
  solely for those extensions.
